## 1. 为什么要在 3GiB 受限环境下测（机制原理）

### 1.1 反直觉事实：hit_rate 与内存压力无关

F2（3GiB）的 `hit_rate=37.36%` 与无限制 n=64 时的 `hit_rate=37.36%` **完全一致**（[`优势场景测试报告`](../rk3588_test_notes/优势场景测试-2026-08-13/RK3588-SLIMARC-优势场景测试报告-2026-08-13.md) §4「hit_rate 与内存限制无关」）。这说明：

> **SLIM-ARC 的预取准确率并没有因内存受限而变好，变的是 baseline 的处境。**

### 1.2 无内存压力时：SLIM-ARC 预取是「冗余」

RK3588 有约 6.4GB 可用内存，80B 模型 45GB。upstream 默认路径（`mmap` + `POSIX_FADV_SEQUENTIAL` + `MAP_POPULATE`）的内核顺序 readahead 已经持续预读，活跃专家页（约 6GB 工作集）能常驻复用，baseline 不慢。SLIM-ARC 的 expert prefetch 此时命中率仅 1.43%、4168MB 浪费（[`测试计划`](../rk3588_test_notes/优势场景测试-2026-08-13/RK3588-SLIMARC-优势场景测试计划-2026-08-13.md) §1.1）——它预取的页 readahead 本来也会读，是重复劳动，速度 ≈ baseline（D 级）。

### 1.3 3GiB 受限时：baseline 的 readahead 被打穿，SLIM-ARC 的「精准」兑现

`MemoryMax=3G` 远小于活跃工作集，page cache 只有 3GB 空间：

- **baseline**：readahead 是「顺序整层预读」，预读的「未来页」会**挤掉当前正要用的页**（3GB 放不下「当前页 + 未来页」），页反复被逐出、反复 major fault，形成缺页抖动 → tg 掉到 **0.70**。
- **SLIM-ARC**：expert prefetch 是「Router 预测驱动、只预取下一步要用的少数专家张量」，不盲目读整层。预取的页是「即将用」的，能在被逐出前被消费。即使仍有 waste（34334MB），也远小于 baseline 整层 readahead 的无谓 I/O → tg **2.21**。

**一句话机制**：「内存充足时谁的预读都够用；内存不够时，只有『精准预取即将用的页』才不浪费那 3GB 页缓存，『顺序整层预读』会把页缓存打穿。」对应归因表见 [`优势场景报告`](../rk3588_test_notes/优势场景测试-2026-08-13/RK3588-SLIMARC-优势场景测试报告-2026-08-13.md) §5.1。

## 3. 前置准备：页缓存冲刷（最容易翻车的一步）

### 3.1 为什么必须冲刷

无 sudo 权限无法 `echo 3 > /proc/sys/vm/drop_caches`。若上一个 run 的模型页已驻留 page cache 且计费在外部 session cgroup，则新 scope 的 `MemoryMax=3G` **可能不触发**（mmap 映射已驻留页时不在新 scope 重复计费）。

**实证**：RSS 补测 R3 首次尝试失效——3G scope 下 VmRSS 达 6280MB，限额未起作用（[`RSS 补测`](../rk3588_test_notes/优势场景测试-2026-08-13/RK3588-SLIMARC-RSS内存峰值补测-2026-08-13.md) §5 第一行）。

### 3.2 冲刷脚本 [`flush-pagecache.sh`](../rk3588_test_notes/优势场景测试-2026-08-13/flush-pagecache.sh)

原理：在**无限制 cgroup** 中分配并写入大量匿名内存（默认 7GB），对系统施加全局内存压力，内核被迫回收全局 page cache（含模型文件缓存页）。

```bash
# 用法：flush-pagecache.sh <目标冲刷量GB，默认7>
bash docs/rk3588_test_notes/优势场景测试-2026-08-13/flush-pagecache.sh 7
```

脚本执行前后各打印一次 `free -m`，用于确认 buff/cache 下降（RSS 补测中 buff/cache 由 ~6.2GB 降至 ~1.4GB，冲刷有效）。

> ⚠️ **必须在无限制 cgroup 中执行**（脚本注释明确）：受限 cgroup 内匿名页不可换出且无法驱逐其他 cgroup 的 page cache，只会触发本 cgroup OOM。

### 4.3 参数逐项含义（被问「每个参数干嘛的」时逐条答）

| 参数 | 含义 |
|---|---|
| `-p 128` | prefill 128 token，测 pp128 |
| `-n 64` | decode 64 token，测 tg64 |
| `-t 4` | 4 线程（RK3588 解码最优线程数，t8 反而更慢） |
| `-r 1` | 单次重复（本组为单次采样，非多次取均值） |
| `--no-warmup` | 无预热，冷启动口径 |
| `-ctk q4_0 -ctv q4_0` | KV cache 量化 q4_0（key/value） |
| `-p MemoryMax=3G` | cgroup v2 内存上限 3GiB |
| `-p MemorySwapMax=0` | 禁 swap，保证受限是硬约束 |
| `env SLIM_ARC_DISABLE=1` | 完全关闭 SLIM-ARC → baseline 模式 |
| `env SLIM_ARC_KV_EVICT=1 SLIM_ARC_KV_SINK=4 SLIM_ARC_KV_WINDOW=512` | 启用 StreamingLLM 式 KV 驱逐（4 个 sink token + 512 滑动窗口） |

> 备注：`systemd-run --user --scope` 输出第一行 `Running scope as unit: run-xxxx.scope`，raw 日志首行即为该输出，是「确实经 cgroup scope 运行」的佐证。

## 6. 复现/讲解时的诚实边界（被追问时主动认，反而加分）

1. **每次跑前必须冲刷页缓存**，否则 `MemoryMax=3G` 可能不触发（R3 首测失效实证）。
2. **F 组是 `r=1` 单次**，无标准差；2.5GiB 档 baseline tg 1.91 反高于 3GiB 的 0.70，是 page cache 驻留窗口敏感的单次波动——只能**档内比较**，不能宣传「内存越小越快」（详细机制见 §6.1）。
3. **F16 KV 是负结果**：SA tg256 1.58 vs baseline 1.94（-18.6%），raw 见 [`优势场景测试-2026-08-13/adv-scenario-F16-sa-2026-08-13.txt`](../rk3588_test_notes/优势场景测试-2026-08-13/adv-scenario-F16-sa-2026-08-13.txt)，原因待查。
4. **没有 S 级场景**（baseline 从不 OOM，只是性能劣化），最佳是 F2/F3 的 A 级 3.16×。真正让 45GB 模型「能跑」的是 llama.cpp 默认 mmap 按需分页，SLIM-ARC 是「受限环境下跑得更快」的优化层。
5. **R 系列 8 线程 ≠ F 系列 4 线程**，R 系列只用于内存峰值证据，不用于吞吐结论。
6. **3GiB 下 cgroup `memory.current` 触顶 3072MB，但进程 VmRSS（4321MB）> 3072MB**：差额约 1.2GB 是模型文件 page cache 页计费在外部 session cgroup（cgroup v2 page cache 按首次缺页 cgroup 计费的正常行为），两类内存数不能直接相减。

### 6.1 为什么 2.5GiB 的 baseline 反而比 3GiB 快（F4 tg 1.91 vs F1 tg 0.70）

这是复核时几乎必被追问的「反直觉」点。答案不是「内存越小越快」，而是**单次采样（r=1）落在 page-cache 驻留窗口的临界点附近，产生了非单调波动**。三个叠加原因：

1. **page cache 初始状态不可控**：本实验无 sudo，用 [`flush-pagecache.sh`](../rk3588_test_notes/优势场景测试-2026-08-13/flush-pagecache.sh) 的「匿名内存挤压法」替代 `drop_caches`，只能把 buff/cache 从 ~6.2GB 压到 ~1.4GB，**无法清零**。每个 run 前残留的 1.4GB 缓存页集合都不同，直接影响第一次缺页行为。

2. **baseline 的 readahead 对驻留窗口是非单调敏感的**：upstream 默认 `POSIX_FADV_SEQUENTIAL` 顺序预读。3GiB 时 readahead 更激进，预读的「未来页」更容易挤掉「当前要用的页」→ 缺页抖动更狠 → tg 0.70；2.5GiB 时内存更紧，readahead 恰好更保守、或预读页更快被逐出，反而偶然形成更好的驻留组合 → tg 1.91。0.5GiB 的窗口差异恰好跨过了某个驻留集临界点，方向不可预测。

3. **执行顺序带来的缓存残留**：F 系列按 F1→F2→F3→F4→F5 串行执行。F4 紧跟在 F3（SLIM-ARC+KV evict）之后，flush 不彻底时可能复用 F3 残留的驻留页；F1 是系列第一组，page cache 最冷。

**铁证**：F4 的 **pp（3.97）也比 F1 的 pp（3.85）略高**——如果只是 decode 阶段策略差异，pp 不该一起变好。pp 和 tg 同时抬升，说明是「F4 这一轮的初始状态整体就比 F1 好」，而不是任何机制在起作用。

**正确结论**：F 系列只能**档内比较**——3GiB 档内 F1→F2（0.70→2.21，3.16×，幅度远超波动，可信）；2.5GiB 档内 F4→F5（1.91→2.21，+16%，幅度小，不能排除波动）。跨档 F1 vs F4 **不可比**。

## 7. 答辩口径（可直接引用）

> 「RK3588 上我们不做『处处都快』的承诺。无限制时 SLIM-ARC 和 baseline 持平；但把内存压到 3GiB 后，baseline 的整层顺序 readahead 会把 3GB 页缓存打穿，Decode 掉到 0.70 t/s，而 SLIM-ARC 的 Router 驱动专家预取只读下一步要用的页，Decode 回到 2.21 t/s，3.16 倍，同时进程内存还少占 338MB。这套结果每一步都有 raw 日志和复现命令，参数、线程数、缓存状态、限额是否生效都记录在案。F4 比 F1 快的反直觉现象，是 r=1 单次采样在页缓存驻留窗口临界点附近的非单调波动，我们只做同档比较，不跨档宣传。」
