# Pi5 4GB × 80B MoE 优化方案（2026-08-13 制定，持续更新）

> 目标：在树莓派 5（4GB RAM + 2GB zram）上优化 Qwen3-Next-80B-A3B（Q4_K_M，38GB，FUSE/NTFS-3G USB3）
> 的推理性能。三条线（WSL x86 / RK3588 / Pi5）共用机制，不破坏兼容性。

## 1. 现状与瓶颈定位（截至 2026-08-13）

### 1.1 已修复的关键回归（本日发现）

**finals 补丁 `issued=0` 回归**：新二进制专家预取完全失效。

| 项 | 旧二进制 (08-13) | 新二进制修复前 | 新二进制修复后 |
|---|---|---|---|
| issued | 8718.8MB | **0.0MB** | 5096.9MB (短冒烟) / 15306.3MB (P12 全长) |
| hit_rate | 31.38% | 0% | 31.79% (冒烟) / 71.16% (P12, CONF+BUDGET) |
| 80B tg32 墙钟 | 886s (P11，同负载) | — | 895s (P12, CONF+BUDGET) |

根因：`issue_expert_willneed` 对未页对齐地址调用 `posix_madvise` → EINVAL 静默失败。
实证与修复见 [`2026-08-13-madvise-alignment-evidence.md`](2026-08-13-madvise-alignment-evidence.md)。

> 注：早期曾把旧 probe 的 457s 当作同负载基线、判定"修复后变慢一倍"，
> 经 §1.4 负载标定证实是工作负载不一致造成的错觉，**无回归**。

### 1.2 瓶颈结构（38GB 模型 / 4GB 内存 ≈ 9.5:1）

1. **I/O 缺页延迟（主因，decode 期 ~86% 墙钟）**：每 token 激活权重
   ≈ 38GB × 3B/80B ≈ **1.4GB**（48 层 × top-10 专家 × 3 张量 × ~860KB/切片）。
   P12 实测页接触速率 (minflt+majflt)×16KB ≈ 63MB/s，CPU 利用率仅 13.6%，
   其余墙钟在等 FUSE 缺页。decode 段 majflt ≈ 880/s（619k/703s），
   FUSE/NTFS-3G 每个缺页 ~1–2ms 用户态-内核态往返，构成硬延迟下限。
2. **CPU/算力（次因）**：A76×4 @2.4GHz，Q4_K 反量化 + GEMV 本身慢；
   45GB/4GB 比例下大部分时间花在等 I/O，CPU 空转（phase-probe 显示 utime 占比低）。
3. **页对齐浪费**：修复后每个专家切片最多损失 2 页（16K 页时 32KB）的首尾对齐裁剪，
   相对 860KB/专家可忽略。

### 1.4 负载标定与 P12 归因（2026-08-13 晚）

- **负载不一致澄清**：旧 probe-10 的 457s 只生成 ~7 token（"The capital of China is
  Beijing." 后即停止，samples=528 ≈ 48层×11token）；P11/P12 用 `-n 32` 长中文 prompt
  （samples=1680 ≈ 48层×35token）。换算单 token decode：旧 ≈ (457−加载)/11 ≈ 28–30s，
  P12 ≈ (895−153)/32 ≈ 23s —— **持平略优，不存在回归**。
- **P11 vs P12**：issued=0 与 issued=15.3GB 墙钟几乎相同（886s vs 895s，
  CPU 时间 119s vs 122s）——预取在当前窗口/预算设置下对总墙钟影响有限，
  瓶颈在缺页延迟本身，不在预取量多少。
- **预算不是瓶颈**：P12 issued ≈ 440MB/token < 614MB/step 上限（§1.5）。
  CONF 门控靠"少而准"把 issued 从 ~800MB/token 降到 440MB，hit_rate 31%→71%。
- **旧二进制 A/B 已失效**：`bin-backup-pre-rebuild/llama-cli-b106-old` 经 ldd 确认
  动态链接当前 `build/bin/libllama.so.0`（已被重编译覆盖），不能再作对照；
  后续 A/B 全部用新二进制 + env 门控切换。

### 1.5 预算管道核实（代码级）

- 总预算：[`llama-model.cpp:1716`](../../src/llama-upstream/src/llama-model.cpp)
  `runtime_owner(slim_arc::default_runtime_budget_bytes())`，默认 1GiB/tick（权重 >6GiB 的 mmap 模型才创建 runtime）；
  自 08-13 起可用 `SLIM_ARC_TOTAL_BUDGET_MB=N` 覆盖（16..1048576 MiB，非法值回退默认）。
- tick 频率：每次 graph compute 一次（[`llama-context.cpp:2520`](../../src/llama-upstream/src/llama-context.cpp)），decode 即每 token 一次。
- 分配：MOE_DECODE `WEIGHT_RATIOS = {0.20, 0.20, 0.60}`（weight/kv/expert，
  [`slim-arc-unified-scheduler.h:118`](../../patches/llama-upstream/slim-arc-unified-scheduler.h)）
  → 专家预算 ≈ 614MB/step；仅当 `SLIM_ARC_EXPERT_BUDGET=1`（或压力准入/常驻门控开启）
  时才通过 `set_expert_budget` 下发限流，默认路径不限流。
- `expert_miss_rate > 0.2` 时专家预算自适应上浮最多 20%。

### 1.6 P13 A0 控制实验结果（2026-08-13 晚）

| 指标 | P11 (issued=0) | P12 (CONF+BUDGET) | P13 A0 (默认无门控) |
|---|---|---|---|
| wall (s) | 886.3 | 895.3 | 931.4 |
| CPU 时间 (s) / 利用率 | 119 / 13.4% | 122 / 13.6% | 120 / 12.9% |
| majflt | 623687 | 630405 | 628551 |
| issued / hit_rate / waste | 0 / – / 0 | 15.3GB / 71.16% / 4.4GB | 28.9GB / 55.54% / 12.8GB |

结论：三组预取量相差近两倍，墙钟却在 ±5% 内、CPU 时间几乎一致 →
再次印证 §1.4：**瓶颈在 FUSE 缺页延迟，不在预取量**。
A0 默认路径 issued 最大但 hit_rate 最低（55.54%），waste 高达 12.8GB
（约整机物理内存 3.2 倍），直接挤占页缓存 → 构成 A2 RECLAIM_WASTE 实验动机。

## 2. 优化方案（按优先级）

### P0：恢复预取功能（已完成）
页对齐修复，issued 恢复。——本日 commit 完成。

### P1：门控组合 A/B（统一负载，测量中）
修复后重跑 08-13 矩阵，统一负载 `-p "请详细介绍量子计算的基本原理" -n 32 --single-turn`：
- A0: 默认（无门控）—— P13 完成（931s, hit_rate 55.54%, issued 28.9GB, waste 12.8GB）
- A1: CONF+BUDGET —— P12 完成（895s, hit_rate 71.16%, issued 15.3GB, waste 4.4GB）
- A2: CONF+BUDGET+RECLAIM_WASTE —— P14 运行中
- A3: CONF+BUDGET+RESIDENCY
- A4（可选）: CONF+BUDGET+SLIM_ARC_TOTAL_BUDGET_MB=256（验证 4GB 端侧缩小总预算）
判据：decode 单 token 时长、majflt/s、hit_rate、waste、CPU 利用率。

### P2：缺页延迟优化（真正的瓶颈，接 §1.4 结论）
瓶颈是 FUSE 缺页延迟（~880 majflt/s × ~1.5ms），不是预取预算。方向：
- 提高 hit_rate：RESIDENCY 常驻热门专家（P3）；预取几何当前构造时固定为
  `prefetch_scheduler_(2, 3)`（n_threads=2、window=3），后续可用 env 门控开放
  worker 数/窗口调参（4GB 下加大窗口会挤页缓存，需 A/B 验证）。
- 降低浪费页挤出：RECLAIM_WASTE 及时 DONTNEED 错误预取页
  （P12 waste 4.4GB，在 4GB 机器上直接挤占有用页缓存）。
- FUSE 层调参（`read_ahead_kb`/`max_read`）需 root，Pi5 无 sudo → 记为局限，
  仅当 WSL/RK3588 侧有权限时验证。

### P3：RECLAIM_WASTE + RESIDENCY 组合
Pi5 4GB 极端内存受限，是 plan 24/26 两个新机制的目标场景：
- RECLAIM_WASTE：错误预取立即 DONTNEED，防止 4GB 内存被无效页占满
  （动机：§1.6 A0 数据显示默认无门控 waste=12.8GB ≈ 物理内存 3.2 倍）
- RESIDENCY：高频专家常驻（budget 上限），减少重复读
风险：DONTNEED 后专家再次命中会二次缺页；需 A/B 验证净收益。

### P4：prefill/decode 阶段策略
80B 首 token 延迟极高（prefill 需全层专家）。短期不做 prompt 缓存优化
（Pi5 demo 场景单轮短 prompt 为主），记录即可。

## 3. 三线兼容性约束

- 所有改动仅在 SLIM-ARC 模块内，env 默认关闭新行为（不改变 upstream 语义）
- 页大小运行时 `sysconf(_SC_PAGESIZE)` 获取（WSL 16K / Pi5 可能 4K 或 16K / RK3588 4K）
- 不触碰上游 llama.cpp 逻辑；patches/llama-upstream 为唯一权威源，
  src 树由 apply-slim-arc.py 生成
