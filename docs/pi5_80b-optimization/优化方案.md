# Pi5 4GB × 80B MoE 优化方案（2026-08-13 制定，持续更新）

> 目标：在树莓派 5（4GB RAM + 2GB zram）上优化 Qwen3-Next-80B-A3B（Q4_K_M，38GB，FUSE/NTFS-3G USB3）
> 的推理性能。三条线（WSL x86 / RK3588 / Pi5）共用机制，不破坏兼容性。

## 1. 现状与瓶颈定位（截至 2026-08-13）

### 1.1 已修复的关键回归（本日发现）

**finals 补丁 `issued=0` 回归**：新二进制专家预取完全失效。

| 项 | 旧二进制 (08-13) | 新二进制修复前 | 新二进制修复后 |
|---|---|---|---|
| issued | 8718.8MB | **0.0MB** | 5096.9MB (短冒烟) |
| hit_rate | 31.38% | 0% | 31.79% |
| 80B tg32 耗时 | ~457s | ~700s+ (thrashing) | 测量中 |

根因：`issue_expert_willneed` 对未页对齐地址调用 `posix_madvise` → EINVAL 静默失败。
实证与修复见 [`2026-08-13-madvise-alignment-evidence.md`](2026-08-13-madvise-alignment-evidence.md)。

### 1.2 瓶颈结构（45GB 模型 / 4GB 内存 = 11.3:1）

1. **I/O 瓶颈（主因）**：工作集远超内存，专家按需从 FUSE/NTFS-3G 读取
   （buffered ~269MB/s）。每 token 需读 ~10 个专家 × 3 张量 ≈ 25MB（top-k=10 时），
   纯顺序读下限 ~10s/token。预取命中（hit_rate ~32%）可将部分读提前到计算重叠区。
2. **CPU/算力（次因）**：A76×4 @2.4GHz，Q4_K 反量化 + GEMV 本身慢；
   45GB/4GB 比例下大部分时间花在等 I/O，CPU 空转（phase-probe 显示 utime 占比低）。
3. **页对齐浪费**：修复后每个专家切片最多损失 2 页（16K 页时 32KB）的首尾对齐裁剪，
   相对 860KB/专家可忽略。

### 1.3 已知可调参数（新二进制门控清单）

| 环境变量 | 作用 | 08-13 旧二进制结论 |
|---|---|---|
| SLIM_ARC_EXPERT_CONF=1 | 置信度门控（仅预测确定时预取） | issued -72.9%, waste -80%, hit_rate 49.17% |
| SLIM_ARC_EXPERT_BUDGET=1 | 每步 I/O 预算上限 | 与 CONF 组合最佳 |
| SLIM_ARC_EXPERT_POP=N | 热门专家频次先验 | 单独效果有限 |
| SLIM_ARC_EXPERT_RECLAIM_WASTE=1 | 错误预取页回收（DONTNEED） | plan 24 新增，未实测 |
| SLIM_ARC_EXPERT_RESIDENCY=1 | 热门专家常驻预算 | plan 26 新增，未实测 |
| SLIM_ARC_PRESSURE_ADMISSION / RESERVE_MB | 压力准入 | 未实测 |
| SLIM_ARC_DECODE_MADV / DYNAMIC_MADV | 阶段 madvise 策略 | RK3588 结论：默认 SEQUENTIAL 最优 |

## 2. 优化方案（按优先级）

### P0：恢复预取功能（已完成）
页对齐修复，issued 恢复。——本日 commit 完成。

### P1：门控组合 A/B（测量中）
修复后重跑 08-13 矩阵，确认 CONF+BUDGET 在新二进制上是否仍是最优组合：
- A0: 默认（无门控）
- A1: CONF+BUDGET
- A2: CONF+BUDGET+RECLAIM_WASTE
- A3: CONF+BUDGET+RESIDENCY
判据：总时长、majflt、read_bytes、hit_rate、waste。

### P2：预取窗口与预算调参
- 当前窗口 window=2、worker=3（构造时固定）。评估提高窗口到 3 是否提升 hit_rate，
  代价是更多内存驻留页（4GB 下可能反噬）。
- EXPERT_BUDGET 默认值调参：当前按每步 per_expert_total×capacity 限制。
  Pi5 上 SSD/FUSE 顺序 269MB/s，4 核算力 tg ~10s/token，理论预算上限
  ≈ 269MB/s × 10s = 2.7GB/step，远超实际需要，预算不是当前瓶颈。

### P3：RECLAIM_WASTE + RESIDENCY 组合
Pi5 4GB 极端内存受限，是 plan 24/26 两个新机制的目标场景：
- RECLAIM_WASTE：错误预取立即 DONTNEED，防止 4GB 内存被无效页占满
- RESIDENCY：高频专家常驻（budget 上限），减少重复读
风险：DONTNEED 后专家再次命中会二次缺页；需 A/B 验证净收益。

### P4：prefill/decode 阶段策略
80B 首 token 延迟极高（prefill 需全层专家）。短期不做 prompt 缓存优化
（Pi5 demo 场景单轮短 prompt 为主），记录即可。

## 3. 三线兼容性约束

- 所有改动仅在 SLIM-ARC 模块内，env 默认关闭新行为（不改变 upstream 语义）
- 页大小运行时 `sysconf(_SC_PAGESIZE)` 获取（WSL 16K / Pi5 可能 4K 或 16K / RK3588 4K）
- 不触碰上游 llama.cpp 逻辑；patches/llama-upstream 为唯一权威源，
  src 树由 apply-slim-arc.py 生成
