# Pi5 4GB × 80B MoE 门控矩阵实验报告（2026-08-13，P13–P16 / A0–A4）

> 本报告为 SLIM-ARC 预取页对齐回归修复后的统一负载 A/B 矩阵总结。
> 背景与瓶颈归因见 [`优化方案.md`](优化方案.md) §1.2–§1.5。

## 1. 实验设置

- **机器**：Raspberry Pi 5，4GB RAM（4049MB）+ 2047MB zram，4 核 aarch64，页大小 16384
- **存储**：模型位于 fuseblk（NTFS-3G，/dev/sda1），缓冲读 269MB/s；Pi5 无 sudo，
  无法 drop_caches（本批为 warm-cache 数据），无法调 FUSE read_ahead_kb/max_read
- **二进制**：`src/llama-upstream/build/bin/llama-cli`（修复页对齐回归后重编译，
  含 SLIM_ARC_TOTAL_BUDGET_MB；旧二进制已被覆盖不可对照，见 §优化方案.md §1.4）
- **模型**：Qwen3-Next-80B-A3B-Instruct-Q4_K_M.gguf（38GB，48 层 MoE，top-10）
- **统一负载**：`-m <80B> -t 4 -c 256 -p "请详细介绍量子计算的基本原理" -n 32 --single-turn`
  （samples=1680 ≈ 48 层 × 35 token，与 08-13 早期 probe 的 11 token 负载不同，不可直接对比）
- **采样工具**：`scripts/profile/phase-probe.sh`（每秒 minflt/majflt/utime/stime/rchar/read_bytes/VmRSS）
- **每组 raw 四件套**：`logs/phase-probe/p{13,14,15,16}-*.{csv,summary,stdout,stderr}`（只读归档，未修改）

## 3. 结论

### 3.1 主结论：瓶颈在 FUSE 缺页延迟，不在预取量（五组证据）
issued 从 0（P11）到 28.9GB（A0）相差悬殊，但六组 wall 全部落在 886–931s（±3%），
majflt 62–63 万、CPU 时间 119–122s 几乎一致。decode 期 majflt/s ≈ 675–700，
每次 FUSE/NTFS-3G 缺页 ~1–2ms 用户态-内核态往返，CPU 利用率仅 12.9–13.7% →
墙钟被缺页延迟支配，任何不减少缺页次数/延迟的软件预取调整都无法改变墙钟。

### 3.2 各门控判定
- **CONF+BUDGET（A1）**：hit_rate 最高（71.16%），issued 减半，是基础配置。
- **RECLAIM_WASTE（A2）**：机制正确且有效——8076 次 DONTNEED 调用、waste 4984MB 全量
  回收、0 失败；墙钟与 A1 持平（896 vs 895s）。在 4GB 上的价值是**防止无效页挤占
  页缓存与内存**，而非提速。推荐与 A4 组合使用。
- **RESIDENCY（A3）**：⚠️ `residency_fallbacks=1632/1632`——Pi5 未开
  `SLIM_ARC_PRESSURE_ADMISSION`（无 cgroup 压力快照源）时，RESIDENCY 不做真正准入
  决策、退化为 legacy 路径；且 wall=931.5s 为六组最差（常驻页挤页缓存嫌疑）。
  **本组为负结果/机制未生效，RESIDENCY 必须与 PRESSURE_ADMISSION 组合才有意义**。
- **TOTAL_BUDGET_MB=256（A4）**：新增 env（T5）端到端生效——issued 15.3GB→4.7GB
  （专家预算 614→154MB/step），hit_rate 66.62%，wall=887.8s **六组最佳**。
  证明 4GB 端侧应缩小总预算、少挤页缓存；默认 1GiB 预算对 4GB 机器过大。

### 3.3 4GB 端侧推荐配置
```
SLIM_ARC_EXPERT_CONF=1 SLIM_ARC_EXPERT_BUDGET=1 SLIM_ARC_TOTAL_BUDGET_MB=256 \
SLIM_ARC_EXPERT_RECLAIM_WASTE=1
```
（A4 + RECLAIM_WASTE 组合未单独实测，属外推；依据是两者机制正交：预算限 issued、
RECLAIM 清 waste，均不引入额外常驻页。）

## 4. 局限性（诚实记录）

1. warm-cache 数据：Pi5 无 sudo 不能 drop_caches，冷启动行为未测。
2. 每组单次运行（单次 ~15 分钟）；组间 ±3% 差异含系统噪声，未做重复取中位数。
3. A4+RECLAIM_WASTE 组合为外推未实测；A3 负结果因压力源缺失，非 RESIDENCY 算法本身缺陷。
4. FUSE 层调参（read_ahead_kb/max_read）需 root，Pi5 无法验证，仅可在 WSL/RK3588 侧探索。
5. 旧二进制对照已失效（ldd 确认被覆盖），历史 457s 数据为不同负载（~7 token），
   已按单 token 速率换算澄清无回归（优化方案.md §1.4）。
