# A44：768 MiB hot-expert cache 筛选

## 更正后的结论

在树莓派 5 的 4 GiB 内存和当前 NTFS-3G/FUSE 模型路径上，将 hot-expert cache 从 A36
候选配置的 512 MiB 扩大到 768 MiB 后，pp16 prefill 只有 `0.0925394 t/s`。相对 A36
两次 cold-run 中位数 `0.20415 t/s`，下降 `54.67%`。但这轮后来发现没有严格保持 A36
控制变量，因此标记为失效；不能把全部回归归因于 768 MiB cache。

这不是环境或旧二进制串用：A44 使用 commit `163d0cfe` 生成的源码，运行时
`libllama.so.0.0.0` SHA256 为
`f82e685f1f2384a92ff40369d657d8f6f4bd85e44d299f8e14feb8dd9b7eee09`。运行期间所有
weight/expert prefetch 都关闭、swap 为 0；但命令误用了不存在的
`SLIM_ARC_EXPERT_HOT_SHARED_MLOCK` 和 `SLIM_ARC_EXPERT_TOTAL_BUDGET_MS`。实际 A36 控制项
`SLIM_ARC_SHARED_MLOCK=1` 与 `SLIM_ARC_TOTAL_BUDGET_MB=16` 没有生效。因此这里只能说明该
组合配置很慢，不能得出“768 MiB 本身导致回归”的结论。

## 固定条件

- 模型：Qwen3-Next-80B-A3B-Instruct Q4_K_M，llama-bench 报告大小
  `48,405,005,312` bytes。
- llama.cpp：`360e1349f0009c5ad99d21e3c4546b707addc68a`。
- SLIM-ARC：`163d0cfe34388c6a3f978cd06f01c47b77bc76cc`。
- `pp=16`、`tg=16`、4 threads、cold cache、swap off。
- hot-expert cache：768 MiB，LRU，首次命中准入；shared mlock 因变量名错误实际未启用。
- weight prefetch：off；expert prefetch：off。

## 结果边界

A44 是早停筛选：prefill 行完整写入后，在 decode 阶段主动终止，因此 `exit=143`、wall=620 秒。
这里只比较完整的 prefill TPS，不使用未完成的 decode，也不把 wall time提升为性能数据。运行结束后
zram 已恢复且 Used=0，模型仍只有 SSD 上的一份。该行 TPS 只作为失效实验的原始观测保留，
不进入单变量优化结论。

`2026-08-15-a44-hot768-tg16-r1/`。
