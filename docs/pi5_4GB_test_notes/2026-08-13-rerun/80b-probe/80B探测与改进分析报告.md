## 3. 分析

### 3.1 为什么 Pi5 上 SLIM-ARC 默认快于禁用（与 RK3588 相反）？

RK3588 上禁用快 3-4×（快 SSD 2.1GB/s + FADV_SEQUENTIAL 顺序预读天然高效，MADV_RANDOM 反而关闭预读）。
Pi5 情况完全不同：

1. **存储慢且是 FUSE**：USB3 实测 buffered 269 MB/s，且 NTFS-3G 走 FUSE，每次缺页都有用户态-内核态往返开销。
2. **内存比例极端**：45GB/4GB = 11.3:1（RK3588 为 45GB/8GB = 5.6:1），工作集远超 page cache，
   顺序预读会把即将用到的权重页也很快挤出，**预取命中直接决定缺页数**。
3. **prefetch 命中省缺页**：默认路径 hit=2735MB，等于 2.7GB 的权重页提前就位，
   每命中 1MB 省约 4ms（269MB/s），理论节省 ~11s 纯 I/O，加上避免的 cache 抖动放大，实测净省 71–75s。
4. **NO_MADV 反而最慢（543s）**：提示在 FUSE 场景，SLIM-ARC 的 madvise 组合（含 >6GB 触发的 MADV_RANDOM）
   恰好抑制了 FUSE 无效的激进预读、配合预取形成更干净的 I/O 模式。

### 3.2 门控开关的效果（改进验证）

| 开关 | issued | waste | hit_rate | 解读 |
|---|---:|---:|---:|---|
| 无门控 | 8718.8 | 5983.2 | 31.38% | 预取激进，68.6% 浪费 |
| CONF | 3179.2 (-63.5%) | 1777.6 (-70.3%) | 44.09% | 2-token 稳定性门控大幅砍掉低置信专家 |
| BUDGET | 5218.9 (-40.1%) | 3650.1 (-39.0%) | 30.06% | 60% I/O 预算限流，hit_rate 微降 |
| CONF+BUDGET | **2360.2 (-72.9%)** | **1199.7 (-80.0%)** | **49.17%** | 双重门控最优：I/O 量最少、命中率最高、耗时不劣化 |

在 4GB 内存下，**减少预取浪费 = 减少 page cache 抖动 = 减少二次缺页**，这是 CONF+BUDGET 组合在
耗时上持平略优（453s 全场最快，P9）的根本原因。该组合应作为 Pi5 80B 的推荐配置：

```bash
SLIM_ARC_EXPERT_CONF=1 SLIM_ARC_EXPERT_BUDGET=1 SLIM_ARC_KV_EVICT=1 \
  ./src/llama-upstream/build/bin/llama-cli -m data/models/Qwen3-Next-80B-A3B-Instruct-Q4_K_M.gguf \
  -t 4 -c 256 -p "..." -n 32 --single-turn < /dev/null
```

### 3.3 内存与 swap 行为

- PEAK_RSS 稳定在 2.78–2.99 GiB（9 组全部 <3GiB），**远低于 4GB 物理内存**，
  印证 mmap 按需分页 + MoE 稀疏激活把 45GB 模型压缩到 ~3GiB 运行时内存。
- 进程级 VmSwap 峰值仅 ~47MB（probe-02 轨迹），zram swap 增长主要来自系统其他进程，
  **80B 推理本身几乎不触发换页**——这是本工作线对赛题"减少运行时物理内存"最有力的实证。

## 4. 瓶颈与局限（诚实记录）

1. **吞吐 0.1 t/s**：prompt 4.9 token + decode 8 token 共耗 ~450s。每 token 需激活 ~3B 参数
   （Qwen3-Next A3B），4 核 A76 @ 2.4GHz 无 i8mm/SVE，纯 Q4_K 计算本身就要 ~2-3s/token；
   叠加 FUSE 缺页（权重页不在 cache 时 ~4ms/MB），二者共同构成瓶颈。**属硬件算力 + 存储介质限制，
   非软件可完全解决**，详见 `瓶颈分析-Pi5-80B.md`（同目录）。
2. **无 sudo**：不能 drop_caches 做严格冷启动；不能调 swappiness。所有测试 buff/cache ≈ 2.7GiB，
   模型页部分预热，耗时偏乐观（真实冷启动预计 +20~60s）。
3. **短任务窗口**：`-n 8/32` 下 prefetch samples=528，长对话下门控行为可能变化，需后续长上下文压测。
4. **FUSE 语义风险**：NTFS-3G 对 madvise 的支持依赖 ntfs-3g 实现，本报告的 A/B 结论绑定该文件系统；
   若未来迁移 ext4，需重新标定。
