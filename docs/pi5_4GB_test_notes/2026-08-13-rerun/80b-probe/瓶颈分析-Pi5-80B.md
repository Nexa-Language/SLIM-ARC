# 瓶颈分析：Pi5 4GB 上 80B MoE 吞吐 0.1 t/s 的归因（2026-08-13）

> 本文档按任务要求记录当前**无法通过软件完全解决**的瓶颈，给出证据与可行的缓解方向。
> 配套数据：同目录 `80B探测与改进分析报告.md`、probe-00~10 raw 文件。

## 1. 瓶颈现象

| 指标 | 值 | 参照 |
|---|---|---|
| Prompt | 0.1 t/s | RK3588 80B: 0.89–2.15 t/s（禁用路径） |
| Generation | 0.1 t/s | WSL x86 8G: 0.08–0.43 t/s |
| 单 token 耗时 | ~5–8 s | — |
| EXIT | 全部 0（功能无异常） | — |

吞吐低但功能完整：45GB 模型在 4GB 内存上正确生成文本，RSS 峰值仅 ~2.9GiB。
瓶颈是**速度**，不是可用性。

## 2. 归因分解（定量估算）

### 2.1 算力瓶颈（主因，占比估算 60–70%）

- Qwen3-Next-80B-A3B 每 token 激活 ~3B 参数（A3B），Q4_K_M 下激活权重 ~1.6–1.8GB/token。
- Pi5：4×Cortex-A76 @ 2.4GHz，**无 AVX2 / SVE / i8mm**（llama.cpp 仅能走基础 NEON 路径），
  Q4_K 点积效率远低于 RK3588 的 i8mm 路径与 x86 AVX2。
- 粗估：4 核 A76 的 Q4_K 有效算力 ~3–5 GOPS 级，跑完 1.7GB 激活权重需 2–3s/token，
  与实测 5s/token 同量级（其余为 I/O 等待，见下）。
- 佐证：Qwen3-4B（Dense 4B，激活全部参数）在同机 tg 仅 4.6 t/s，
  按 4B/3B 激活比例折算，80B-A3B 的纯算力上限也就 ~3–6 t/s 的理想值，
  实际 0.1 t/s 说明 I/O 等待把有效算力利用率压到了 ~3–5%。

### 2.2 I/O 瓶颈（次因，占比估算 30–40%）

- 存储链路：USB3 移动硬盘 → NTFS-3G（**FUSE 用户态文件系统**）→ page cache → mmap。
- 实测 buffered 读 269 MB/s（probe-00-env），但这是大文件顺序读；
  **随机缺页场景下 FUSE 每次 page fault 需内核↔ntfs-3g 用户态往返**，单次缺页开销远大于 ext4。
- 45GB 模型 vs 4GB RAM：工作集 11.3:1 超出 page cache，每层 MoE 的专家权重
  大概率需要重新缺页（prefetch hit_rate 仅 31–49% 即证明 51–69% 专家仍需现场读盘）。
- 每 token 若需现场读取 ~0.8–1GB 未命中专家：269MB/s 下 ≈ 3–4s，与实测剩余耗时吻合。

### 2.3 内存压力（轻微）

- 进程 VmSwap 峰值仅 ~47MB，zram 不是瓶颈。
- 但 page cache 容量（~2.6GiB 可用）远小于工作集，**cache 抖动**（预取挤出 + 缺页重读）
  是 I/O 瓶颈的放大器——这正是 CONF+BUDGET 门控能改善 hit_rate 的原因。

## 3. 为什么软件层面难以根治

| 手段 | 为什么不行/有限 |
|---|---|
| 改 madvise 策略 | 已在用；NO_MADV 更慢（543s），说明当前组合已接近 FUSE 场景最优 |
| 加大预取 | issued 已达 8718MB 时 hit_rate 仅 31%，更激进只会加剧 cache 抖动（RK3588 教训） |
| KV eviction | 短上下文不触发；对权重 I/O 无帮助 |
| 换页/锁定 | mlock 45GB 不现实（物理内存 4GB） |
| **算力** | A76 无 i8mm/SVE，llama.cpp 内核效率受限，纯软件无法改变 ISA 能力 |

## 4. 可行的缓解方向（按投入排序）

1. **存储介质 A/B（低成本，优先）**：将 80B 复制到 ext4 分区（microSD 剩余 11GB 不够，
   需 USB 盘改 ext4 或新增分区）后重测。若 tg 提升明显，则证明 FUSE 是主要可解部分，
   建议正式测试固定 ext4；若提升有限，则坐实算力为主瓶颈，归档为硬件限制。
2. **预取门控保持 CONF+BUDGET**：已验证 hit_rate 49.2% 为最优，waste -80%。
3. **批处理/投机类优化（中期）**：llama.cpp 的 speculative decoding 需 draft 模型，
   4B 可做 80B 的 draft（Qwen3-4B 与 Qwen3-Next 词表兼容需验证），若接受率可观，
   等效放大 decode 吞吐——**这是纯软件路线里最可能突破 0.1 t/s 的方向**，列入后续计划。
4. **量化再压缩（谨慎）**：IQ4_XS（80B 约 36GB）可进一步降 I/O，但 Pi5 无 i8mm，
   IQ 解码的计算开销可能抵消收益，需实测后再定。

## 5. 结论

Pi5 4GB 上 80B 的 0.1 t/s 是 **A76 算力（无 i8mm/SVE）+ FUSE 随机缺页** 双重硬件/介质瓶颈的
叠加结果；SLIM-ARC 已把"能跑、内存可控（<3GiB RSS）、预取浪费最小化"做到位，
并在该环境下默认路径反超禁用 13%。继续提升吞吐属于硬件/介质层面约束，
软件侧剩余空间集中在 speculative decoding 与存储介质替换验证。
