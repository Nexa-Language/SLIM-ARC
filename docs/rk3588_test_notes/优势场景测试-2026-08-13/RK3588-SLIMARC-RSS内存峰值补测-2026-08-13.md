## 2. 补测方法

1. `/usr/bin/time` 在本机**不存在**（`ls: cannot access '/usr/bin/time'`），
   故按任务预案采用后台监控脚本法：
   - 脚本 `rss-monitor-run.sh`：后台启动 llama-bench，每 0.5s 轮询
     `/proc/<PID>/status` 的 `VmRSS`/`VmHWM` 取最大值；scope 场景同步轮询
     cgroup `memory.current` 取峰值。
   - 内核 5.10 的 cgroup v2 **没有 `memory.peak` 接口**（该接口 kernel 5.15+
     才引入；已实测确认 `/sys/fs/cgroup/.../memory.peak` MISSING），
     故以 `memory.current` 轮询峰值作为 cgroup 侧内存峰值的近似下界。
   - 进程匹配用 `pgrep -x llama-bench`（按 comm 精确匹配），
     避免误匹配 systemd-run/sh 包装进程。
2. 每个场景测试前执行 `flush-pagecache.sh`（无 sudo 权限，无法 drop_caches；
   用无限制 cgroup 中分配 6GB 匿名内存的方式挤压回收全局 page cache，
   buff/cache 由 ~6.2GB 降至 ~1.4GB，冲刷有效），保证 cgroup 限制真实生效。
3. 每个场景 timeout 600s，全部非交互自动执行。

## 4. 分析：SLIM-ARC 内存开销 vs baseline

1. **无限制场景（R1 vs R2）**：SLIM-ARC 的 VmHWM 峰值比 baseline
   **高 836 MB（+13.5%，6180→7016 MB）**。这部分额外开销对应 expert
   prefetch 缓冲区（R2 日志 SLIM-ARC-METRICS：issued=54928.1MB，
   hit_rate=40.69%），即以常驻内存换取预取命中。
2. **3GB 限制场景（R3 vs R4 vs R5）**：三个配置的 cgroup 计费均恰好触及
   3072 MB 上限，说明 MemoryMax=3G 限制真实生效。进程级 VmHWM 峰值
   SLIM-ARC 反而**低于 baseline**：
   - SLIM-ARC vs baseline：3986 vs 4324 MB，**低 338 MB（-7.8%）**；
   - SLIM-ARC+KV_EVICT vs baseline：3951 vs 4324 MB，**低 373 MB（-8.6%）**。
   即受限环境下 SLIM-ARC 的预取/KV 驱逐策略会主动控制驻留集，
   不会比 baseline 占用更多进程内存。
3. **VmRSS > memory.current 的原因说明**：3G 场景中进程 VmRSS（如 R3 4321 MB）
   高于 scope 内 memory.current 峰值（3072 MB）。差额约 1.2GB 是模型文件
   的 page cache 页仍计费在外部 session cgroup（flush 后幸存、未重新计费的
   缓存页），映射进进程时计入 RSS 但不计入本 scope。这是 cgroup v2 page cache
   按首次缺页 cgroup 计费的正常行为，已在监控日志中保留 proc_cgroup 供核查。
