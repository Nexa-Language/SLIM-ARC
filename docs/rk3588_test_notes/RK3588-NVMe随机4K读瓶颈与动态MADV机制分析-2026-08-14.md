## 1. 问题陈述

SLIM-ARC 初版在 RK3588（Orange Pi 5 Plus，8GB RAM，NVMe SSD 顺序读 2.1GB/s）上对 Qwen3-Next-80B-A3B Q4_K_M（45.09GiB）**静态全量**设置 `POSIX_MADV_RANDOM`，造成严重负优化【实测，B1–B7 矩阵】：

| 编号 | 配置 | pp (t/s) | tg (t/s) |
|:---:|:---|:---:|:---:|
| B1 | SLIM-ARC 全开（含 MADV_RANDOM） | 0.39 | 0.23 |
| B2 | `SLIM_ARC_DISABLE=1`（上游默认） | **2.02** | **0.89** |
| B3 | 仅禁用 MADV_RANDOM | 1.41 | 0.65 |
| B4 | 仅禁用预取 | 0.37 | 0.24 |

- B1 vs B3：**MADV_RANDOM 单项**造成 pp 3.6×、tg 2.8× 损失；
- B1 vs B4：预取开关在 RANDOM 背景下无差异（随机小读已把链路打崩，预取无从发挥）；
- 阶段 2a 复测（llama-bench -p 32 -n 16 -t 4）：静态 RANDOM 全开 0.44/0.26 vs 上游禁用 2.74/1.41，即 **decode 负优化 5.4×**【实测】。

而同一套机制在 WSL（x86 + NVMe）上是正优化（RSS 45GB→2GB，节省 98%）。**同一机制、两类硬件、相反结论**——本文解释这一差异，并说明动态 MADV 的设计。

## 2. NVMe 读数据的标准流程（4 步）

一次 4KB 缺页读盘的完整路径【机制】：

1. **CPU 发请求**：CPU 经内核块层/NVMe 驱动，把「读闪存地址 X 的 4KB，DMA 到内存地址 Y」写入提交队列（SQ）；
2. **NVMe 执行**：SSD 主控从闪存取数，经 PCIe 总线 DMA 写入内存 Y；
3. **NVMe 发中断**：主控在完成队列（CQ）写条目并发中断（MSI-X）；
4. **CPU 处理中断**：CPU 响应中断、取回数据、唤醒等待线程，用户态继续执行。

随机 4K IOPS = 1 ÷（单趟固定开销 ÷ 并行度）。**三个关键参数**决定这个值：

| 参数 | 含义 | 决定什么 |
|:---|:---|:---|
| **队列深度（Queue Depth）** | CPU 能同时挂在 NVMe 上的「待办请求」数 | 并行度：QD 高才能把闪存多通道并行跑满 |
| **中断粒度（Interrupt Coalescing/向量数）** | 每完成多少请求发一次中断、每队列有无独立向量 | 通知成本：向量不足→共享中断→CPU 轮询多队列，额外开销 |
| **单次固定开销（Per-I/O Fixed Overhead）** | 与数据量无关的每趟成本：内核态切换、PCIe 往返、主控解析、中断响应、上下文切换 | 延迟下限：4K 小读中固定开销占比可达 80%+ |

**【机制】核心不对称**：顺序大块读一次固定开销摊到 128KB–1MB，是**带宽受限**（吃满 2.1GB/s）；随机 4K 读每页付一次全额固定开销且 mmap 缺页是**同步、QD≈1** 的串行路径，是**延迟受限**——NVMe 的多队列并行能力在 demand paging 路径下天然作废。

## 3. RK3588 上三个参数为什么被「砍配置」

> 本节为外部分析框架，**硬件规格数字均为【假设】**，方向与仓库实测自洽；§6 给出板上验证命令。

### 3.1 队列深度：DMA 描述符环与中断向量受限【假设】
- 分析称 RK3588 PCIe 控制器 DMA 描述符环仅 128、全局 MSI-X 向量仅 32（桌面平台数百至上千），多队列（multi-queue）跑不满，有效 QD 被压到几十甚至个位数。
- 与实测的自洽点：RANDOM 解码期 SSD 仅 **500–560MB/s，为 2.1GB/s 容量的 1/4，盘未饱和**【实测】——盘有并行能力但请求喂不饱；且**加线程（t8）负收益**【实测】——若瓶颈在盘的并行上限，堆并发应至少持平而非变差，说明串行点在请求侧路径。

### 3.2 中断粒度：向量不足→共享中断→聚合开销【假设】
- 32 个 MSI-X 向量不足以每 I/O 队列独立分配，多队列共享向量，中断到来后 CPU 需轮询多个 CQ；为保 4K 低延迟又不敢粗化聚合，中断频率高。
- **与实测的冲突修正**：原分析称「CPU 一半以上时间处理中断」，与仓库实测 **CPU 空闲 40–45%、iowait 仅 9–13%**【实测】**不符**。实际形态不是「中断风暴打满 CPU」，而是：**发起 fault 的线程被同步路径串行卡住、其余核空转等数据**。答辩时不要引用「中断占半 CPU」。

### 3.3 单次固定开销：I/O 路径长、核弱【假设+机制】
- 【机制，确定】RK3588 的 NVMe DMA 需经 SoC 内 AXI 互联与（若启用的）SMMU/IOMMU 才到 LPDDR，路径长于 x86 的「PCIe 直连内存控制器」；A76/A55 单核处理 fault/中断/上下文切换慢于桌面 x86。
- 【假设，量级】原分析称 RK3588 单趟 4K 固定开销 ~150µs vs 桌面 ~50µs（3×）。该量级与「QD1 随机 ≈ 几十 MB/s」的推算自洽，但**未在本板实测**。
- 【假设】顺序读 2.1GB/s 与 PCIe 3.0 x2 有效上限吻合（x4 消费盘通常 3.5GB/s+），推测 M.2 链路位宽或盘型号受限；该因素只压**顺序带宽天花板**，不解释随机负优化，列为次要。

### 3.4 三参数叠加效应（回扣问题）
- **顺序大块读**：固定开销只付一次、QD 需求低 → 仍能跑满 2.1GB/s【实测】；
- **随机 4K 缺页**：每页付全额固定开销（高）× 并行度低（QD 受限）× 通知成本高（共享中断）→ 有效随机 IOPS 被压到桌面级的 1/5–1/10【假设量级，方向有 §4 实测佐证】。
- **边界澄清**：这是「面向边缘的低功耗 SoC」的链路配置问题，不是 ARM 架构问题——服务器级 ARM（如 Graviton3）三参数拉满，随机 IOPS 不差。

### 4.1 采纳（框架与数据互相印证）
| 分析论断 | 印证实测 | 出处 |
|:---|:---|:---|

| 瓶颈在请求侧串行路径而非盘 | 加线程负收益；CPU 空闲 40–45%、wa 9–13% | 改进记录.md 阶段 8 |
| MADV_RANDOM 是负优化主因 | B1 vs B3：3.6×/2.8×；阶段 2a：5.4× | 性能分析.md §2.2 |
| 固定开销摊薄即解药 | 动态 MADV 后 prefill 0.44→2.82 t/s（+541%），decode 0.25→1.40（消除负优化、追平上游） | stage2a/2b summary |

### 4.2 修正（原分析中与实测冲突或夸张处，答辩禁用）
1. ❌「每生成一个 token 要发**几十万次** 4K 读」→ 量级错误。Pi5 同模型实测 majflt 62–63 万 ÷ 1680 samples ≈ **每 token 数百至数千次**【实测，phase-probe】；「几十万」是整轮运行总量。
2. ❌「CPU 一半以上时间处理中断」→ 与 CPU 空闲 40–45% 矛盾；实际是同步 fault 串行卡线程 + 其余核空转。
3. ❌「随机 IOPS 直接砍到 1/8」「1/5–1/10」等具体倍数 → 无本板 fio 实测，仅可作量级直觉，引用时注明未测。

### 4.3 保留为假设（方向可信、数字待测）
DMA 描述符环 128、MSI-X 32、PCIe x1/x2、SMMU 路径、150µs vs 50µs——见 §6 验证命令。

### 4.4 跨平台旁证（同一框架的第三个数据点）
Pi5（FUSE/NTFS-3G 挂载）单次缺页 ~1.5ms【实测，phase-probe P11–P16】：fault 固定开销更高一档，导致「预取量多少都不重要、瓶颈= fault 次数」。三台设备（WSL x86+NVMe / RK3588 ARM+NVMe / Pi5 ARM+FUSE）在「固定开销 × 并行度 × 工作集 churn」同一坐标系下行为全部自洽。

## 5. 动态 MADV 机制说明（SLIM-ARC 的解法）

### 5.1 问题根源
初版在模型加载时对 45.1GiB mmap 区域**一次性静态**设置 `MADV_RANDOM`（触发条件 `msz > 6GiB`），不区分阶段：既惩罚了 prefill 的顺序扫描（关掉 readahead），又让 decode 在 RK3588 上以延迟受限的小读主导 I/O。

### 5.2 机制设计
- **阶段感知切换**：`register_mmap_region()` 记录所有 mmap 区域；`set_phase()` 在 prefill/decode 切换时调用 `apply_dynamic_madv()` 对全部区域重设建议：
  - **prefill/加载阶段** → `POSIX_MADV_SEQUENTIAL`：权重逐层顺序扫描，吃满内核顺序预读与 SSD 顺序带宽；
  - **decode 阶段** → 默认 `MADV_RANDOM`（内存充足场景：fault 便宜、省 98% 无用预读，WSL 正优化来源），可经 `SLIM_ARC_DECODE_MADV=NORMAL` 覆盖为保留预读（RK3588 场景）。
- **环境变量**：`SLIM_ARC_DYNAMIC_MADV`（默认启用，=0 回退不设建议）、`SLIM_ARC_DECODE_MADV`（RANDOM/NORMAL）。
- LD_PRELOAD 拦截验证：prefill 期 SEQUENTIAL×5、decode 期 RANDOM×15，切换真实生效【实测】。

### 5.3 效果【实测】
| 配置 | pp (t/s) | tg (t/s) |
|:---|:---:|:---:|
| 改进前 静态 RANDOM 全开 | 0.44 | 0.26 |
| 动态 MADV 全开 | **2.82**（+541%） | 0.25 |
| 动态 MADV + decode=NORMAL（RK3588 最优） | 2.81 | **1.35–1.40**（负优化消除，追平上游 1.41） |

### 5.4 为什么两台机器 decode 策略相反（机制边界）
- **WSL/x86+NVMe**：单趟固定开销低、多核可堆队列深度 → 随机按需分页「付得起」，省下的 98% 无用预读是净收益，Router 预测预取有兑现空间；
- **RK3588/ARM+NVMe**：45GB/8GB 工作集 churn 严重（每 token 新页数百 MB，缓存约 8–10 token 轮转一遍），decode 反正每步碰盘；此时每趟固定开销高、并行度低 → **顺序预读把固定开销摊薄到 128KB 大块**，且专家张量文件内连续、「顺带」预读常命中下一步 → SEQUENTIAL 赢。
- **设计哲学**：机制正确 ≠ 处处有效。SLIM-ARC 把访问模式做成**可按阶段、按设备适配的旋钮**，而非全局银弹——这正是赛题「全局系统观念」的落点。

## 7. 答辩口径（可直接引用）

> 「随机 IOPS 慢不是 NVMe 盘的问题——实测它 3/4 带宽在闲置。慢的是 RK3588 这条 I/O 链路：同步 4K 缺页把队列深度压到 1、每趟固定开销（内核 fault 路径 + SoC 内 DMA/SMMU 路径 + 弱核中断处理）占比极高，顺序预读靠 128KB 大块把固定开销摊薄，所以赢。SLIM-ARC 的动态 MADV 就是让访问模式按阶段、按设备去适配这条链路的系统边界：prefill 顺序吃带宽，decode 在 x86 用随机按需省内存、在 RK3588 保留预读保吞吐。机制没有好坏，只有与硬件场景的匹配。」
