## 阶段 0：基线确认

- 环境：RK3588 8GB，SSD 2.1GB/s，Qwen3-Next-80B Q4_K_M（45.09GiB）
- 短上下文基线（llama-bench -p 32 -n 16 -t 4）：
  - 全开（静态 RANDOM）：pp 0.44 / tg 0.26
  - 禁用：pp 2.74 / tg 1.41
- **确认负优化基线**：全开比禁用慢 5-6×

## 阶段 1：零代码优化链测试

- KV q4_0 量化：短上下文无显著性能影响（pp 0.43/0.26 全开、2.70/1.42 禁用）→ 量化主要省内存，非提速
- **结论**：短上下文瓶颈是 MADV_RANDOM 关闭预读 + 计算，非量化。转向代码改进。

## 阶段 2a：动态 MADV 切换（prefill 用 SEQUENTIAL）

### 修改
- `slim-arc-prefetch.cpp`：`register_mmap_region` 初始设 `POSIX_MADV_SEQUENTIAL`；新增 `apply_madvice_to_regions()`、`apply_dynamic_madv()`
- `slim-arc-prefetch.h`：`set_phase()` 触发 `apply_dynamic_madv()`；前置声明
- `apply-slim-arc.py`：model-loader 去掉静态 RANDOM 改 dynamic（修复重复插入 bug：旧块正则清理）

### 验证
- LD_PRELOAD 拦截：prefill→SEQUENTIAL、decode→RANDOM 确认触发
- **prefill 0.44 → 2.82（+541%）**，负优化消除

### 遇到的问题
- `apply_dynamic_madv` 编译错误（header 内联调用顺序）→ 前置声明修复
- model-loader 出现新旧两个 MADV 块 → apply-slim-arc.py 幂等清理逻辑修复

## 阶段 2b：decode 优化（消融发现 RANDOM 是负优化）

### 消融实验（decode 阶段不同建议）
| decode 建议 | pp | tg |
|:---|:---:|:---:|
| RANDOM（按需分页） | 2.82 | **0.25** |
| SEQUENTIAL（顺序预读） | 2.81 | **1.35** |
| NORMAL（内核默认） | 2.57 | **1.41** |

### 发现
RK3588 45GB/8GB 极端比例下，decode 阶段 MADV_RANDOM 严重拖慢（0.25 vs 1.40，5.4×）。原因：工作集完全放不下，decode 每次都要 SSD 读，RANDOM 随机读远慢于 SEQUENTIAL 顺序预读。

### 决策
- 默认 decode 用 **SEQUENTIAL**（避免 RANDOM）
- 保留 `SLIM_ARC_DECODE_MADV=RANDOM/NORMAL` 供内存充足场景覆盖
- **结果**：全开 tg 0.26 → 1.40（+438%），追平禁用

## 阶段 3：MADV_RANDOM 粒度细化评估

- **决策：RK3588 端侧无需实施**。消融已证明完全避免 RANDOM（全阶段 SEQUENTIAL）最优；粒度细化（仅专家区域 RANDOM）属于内存相对充足场景（WSL）的优化，RK3588 保持 SEQUENTIAL 即可。

## 阶段 4：长上下文 + KV eviction 协同验证

- 长上下文（p512 n128）：全开 6.09/2.08 vs 禁用 6.33/2.15，差距 ~4%
- KV eviction 协同：`ENABLED` + 驱逐日志正常，动态 MADV 不干扰，输出连贯
- **结论**：负优化从 4-6× 消除到 ~0-4% 持平

## 最终改进效果

| 场景 | 改进前全开 | 改进后全开 | 禁用 |
|:---|:---:|:---:|:---:|
| 短上下文 (p32n16) | 0.44/0.26 | 2.84/1.40 | 2.74/1.41 |

> SLIM-ARC 从 4-6× 负优化转为与禁用持平（~0-4%），且保留预取/KV eviction 机制。

## 阶段 5：预取/专家预取/统一调度生效排查

背景：动态 MADV 追平禁用后，需确认 SLIM-ARC 的"层预取 + MoE 专家预取 + 统一 I/O 调度"是否真正在解码中生效。加临时调试日志（`[SLIM-ARC-DBG]`）逐级观测。

### 排查结果（Qwen3-Next-80B, 短测试 n=16）

| 观测点 | 修复前 | 修复后 |
|:---|:---:|:---:|
| `register_expert_tensor`（专家张量注册） | 144 次 | 144 次（48 层 × 3：down 440MB/gate 302MB/up 302MB，每层 512 专家） |
| `cache_router_experts`（router 提取） | 0 → 528 → 回归 0 | **912 次**（每 decode 各层 top-10 提取） |
| `get_cached_experts`（跨层查询命中） | 0 | 846 次 |
| `issue_expert_willneed`（专家 WILLNEED 下发） | **0 次** | **846 次**（layer 1-47，每层 10 专家 × 3 张量） |

### 三个根因（逐层排除）

1. **层号解析失败**：`ffn_moe_topk-<N>` / `gate-<N>` 节点名无 `blk.` 前缀，`tensor_layer_from_name` 失败 → router hook 层号用 `strrchr(t->name,'-')+atoi` 回退解析。
2. **层范围扫描失败**：decode 图节点导致 `min_layer=INT_MAX` → 预取块整体跳过 → 层扫描也加 `-<N>` 后缀回退。
3. **幂等性回归 bug**：apply-slim-arc.py 用 `'ffn_moe_topk' not in content` 判断 router 块是否已插入，但层扫描注释中出现了 `ffn_moe_topk` 字样 → 误判已存在而跳过插入，`cache_router_experts` 从 528 回归 0 → 插入标记改为 `'cache_router_experts'`。

### 附带修复：apply-slim-arc.py 镜像同步断裂

- 根因：`patches_dir = "patches/llama-upstream"` 硬编码相对路径，从 `/home/orangepi` 运行（脚本在 `SLIM-ARC/scripts/`）时找不到 patches，Step 1 复制全部 WARNING，违反 red-line 镜像同步规则。
- 修复：`patches_dir` 基于脚本自身位置（`__file__` 上溯两级）解析，任意 CWD 均可正确复制。
- 验证：8 个 slim-arc 文件 `diff` 全部 SYNC。

**结论**：专家预取机制经 3 个 bug 修复后**确认真正触发**（846 次 WILLNEED 下发），机制本身正确。

## 阶段 6：路由预测精度诊断（为何预取无收益）

在 `cache_router_experts` 中加自包含诊断，量化两种预测器精度（覆盖缓存前计算与上一 token 实测路由的重叠度）：

| 预测器 | 含义 | 实测精度 |
|:---|:---|:---:|
| **temporal（时间）** | 同层上一 token 路由 → 本 token | **34.9%** |
| **spatial（空间，原实现）** | 上一层上一 token 路由 → 本层 | **4.5%** |

- 随机基线 10/512 ≈ 2%。temporal 是随机的 17.5×，spatial 仅 2.25×。
- **根因**：原实现空间预测 95% 是无效预取，在带宽受限场景抢占 I/O，这正是专家预取"触发但无收益"的原因。

## 阶段 7：预测器改进 spatial → temporal

### 修改
- apply-slim-arc.py 两分支：`get_cached_experts(l - 1)` → `get_cached_experts(l)`（用同层上一 token 路由预测本层）。

### A/B 验证（干净代码，无调试打印）
- llama-bench p32n32 交错：ON 平均 pp 2.76/tg 1.69；OFF 平均 pp 2.73/tg 1.72 → **解码中性（-1.5% 噪声内）**
- llama-cli n=128 长生成交错：生成 ON 1.9 / OFF 1.9（持平）；**prefill ON 2.2-2.3 vs OFF 2.0（+10-15%，动态 MADV 收益）**

**结论**：时间预测精度提升 7.8×，但 RK3588 解码仍中性 → 瓶颈不在"预测准不准"。

## 阶段 8：瓶颈根因分析（解码非 SSD I/O 受限）

### 实验 1：线程消融（n=64, 全开）
| 线程 | Generation |
|:---:|:---:|
| t4 | **1.9** |
| t6 | 1.8 |
| t8 | **1.3**（更差）|

> 加线程反而变慢 → 非计算受限；符合 I/O/内存带宽受限特征。

### 实验 2：vmstat 实测（n=128 解码期）
| 指标 | 值 | 含义 |
|:---|:---|:---|
| SSD 读 | ~500-560 MB/s | 远低于 2.1GB/s 容量，**未饱和** |
| wa（I/O 等待） | 9-13% | 非 I/O 饱和 |
| CPU 空闲 | 40-45% | 计算未满载 |

### 综合根因
RK3588 80B 解码**不是 SSD I/O 受限**，而是受**计算吞吐/并行度/内存带宽**共同限制（CPU 空闲 45%、SSD 只用 1/4 带宽、加线程负收益）。因此：

> **I/O 预取类机制（层预取 + MoE 专家预取 + WILLNEED）对解码提速存在物理上限**——瓶颈不在"数据到达速度"，预取无法消除计算/内存带宽瓶颈。

### SLIM-ARC 在 RK3588 的真实价值（诚实的边界）
1. **消除负优化**：静态 RANDOM 的 4-6× 负优化 → 动态 MADV 追平禁用（decode 0.26→1.40）。
2. **prefill 提速 +10-15%**：SEQUENTIAL 顺序预读（长 prompt 场景明确）。
3. **长上下文能力**：KV eviction 使 45GB/8GB 极端比例下可长上下文运行不 OOM（能力收益，非速度）。
4. **专家预取机制**：已验证正确触发（temporal 预测 35% 精度），在 RK3588 解码中性，是正确但不适用于该瓶颈的机制。

# 阶段 11-14：基于文献 moe_cpu_memory_limited_survey.pdf 的 4 点改进（2026-08-09）

- 文献主线："内存受限 CPU 场景，瓶颈从纯计算转为分层内存的搬运/缓存/预测/调度；先做可观测，再按置信度/预算优化"。
- 原则：保留原机制，4 点全部为 `prefetch_scheduler` 的**增量可观测/可配置**逻辑，默认不改原始行为（除指标常开）。

## 阶段 11：改进 1——专家预取可观测性指标（foundation）

- 依据：文献"先做可观测的 memory hierarchy runtime" + 必须建立指标（hit rate、wasted bytes）。
- 实现：`prefetch_scheduler` 增加 `expert_prefetch_bytes_/expert_hit_bytes_/expert_waste_bytes_/router_samples_`；
  `issue_expert_willneed` 记录实际下发集合（`last_prefetched_experts_`），`cache_router_experts` 用实际路由对照计算 hit/waste；析构 `dump_metrics()` 输出。
- 附带修复：同一层多个 `ffn_moe_topk` 节点导致重复计数 → 计数后清空集合。
- 结果（n=64 基线）：issued=27.8GB、hit_rate=31.05%（temporal 基线命中率，与阶段 6 诊断 34.9% 一致）。**指标自洽、可观测目标达成**。

## 阶段 12：改进 2——置信度门控专家预取（WIN）

- 依据：文献"按置信度区分 prefetch/回退"（CommitMoE/DALI）。
- 实现：`cache_router_experts` 滑动 2-token 历史（cached/prev）；`SLIM_ARC_EXPERT_CONF=1` 时仅预取**连续两 token 都激活的稳定专家**（A_t ∩ A_{t-1}），低置信度不浪费 WILLNEED、依赖按需分页。
- 结果（n=64）：
  | 配置 | issued | hit_rate | tg(cli) |
  |:---|:---:|:---:|:---:|
  | baseline | 27.8GB | 31.1% | 1.9 |
  | **CONF=1** | **12.1GB** | **55.4%** | 1.9 |
- llama-bench A/B（p32n32 交错×2）：base 平均 pp 2.81/tg 1.75；conf 平均 pp 2.89/tg 1.77（pp +3%/tg +1%）。
- **结论**：命中率 +24pp、下发字节 -56%、速度无损失微升。**明确收益，推荐开启**（默认关闭待审核）。

## 阶段 13：改进 3——专家预取纳入统一 I/O 预算（admission control）

- 依据：文献"用调度隐藏 I/O / admission control（按 budget 限流）"。
- 实现：`prefetch_scheduler::expert_budget_`（0=不限）；`unified_io_scheduler::tick()` 在 `SLIM_ARC_EXPERT_BUDGET=1` 时下发 `budget.expert_bytes`（MOE_DECODE 占比 60%≈600MB）并每 step 重置累计用量；`issue_expert_willneed` 按每 step 累计预算截断。
- 修正：初版按"单次调用"预算（每层 ~20MB 远小于 600MB）从不触发 → 改为**每 step 累计预算**。
- 结果（n=64）：issued 27.8→25.8GB（-7%），hit_rate 29%，tg 1.9。
- **结论**：机制正确（能截断突发），但 RK3588 解码非 I/O 受限，收益有限（-7% I/O、速度中性）。conf+budget 组合：issued 12.1GB、hit_rate 54%、tg 2.1。

## 阶段 14：改进 4——组合预测器 temporal + 热门专家（诚实负结果）

- 依据：文献 ReMoE（提高 locality）/DALI（workload-aware cache）。
- 实现：`cache_router_experts` 累加每层专家激活频次；`SLIM_ARC_EXPERT_POP=K` 时预取 temporal ∪ top-K 热门专家。
- 结果（n=64，K=16）：issued **72.6GB（+161%）**、hit_rate **19.3%（下降）**、tg 2.0。
- **结论（诚实负结果）**：热门专家与当前 token 路由重叠低，并集稀释命中率、放大 I/O。运行时"热门并集预取"在该 workload 上不成立；文献的 ReMoE 需**训练 router 提高 locality**（出本框架范围）。保留为默认关闭的可配置项，供后续验证。

## 阶段 15：最终状态

- 4 点改进全部实测；指标常开，CONF/BUDGET/POP 均为 env 可配置（默认关闭，保持原始行为）。
- 推荐：`SLIM_ARC_EXPERT_CONF=1`（明确收益）；`SLIM_ARC_EXPERT_BUDGET=1`（突发截断，非 I/O 受限时收益有限）；`SLIM_ARC_EXPERT_POP` 不建议开启。
- 镜像同步 8/8；编译干净（仅 2 个既有 unused-parameter 警告）。
